## 2. 背景与研究目标（已确认）

早期讨论涉及完整聊天获取与归档。用户随后明确：不一定永久保存，只需分析每天内容，跳过无趣消息，关注感兴趣的信息，看完后可不继续保存（S2，用户回合 `a952cf48-0d43-42e7-af33-b12900724c19`）。因此当前定位是个人 QQ 信息雷达，而非永久聊天档案库。

用户期望自动接收聊天信息、尽量保证完整、按关注主题筛选，并定位信息来源；优先复用已有项目（S3，`e2ee2695-ff48-47c2-b0cc-b428a20be0fc`）。

成功目标：在可说明完整性边界的分析窗口内，将大量消息压缩为值得阅读的主题与摘要；每个结果能够追溯到原消息或明确说明来源不可用；降低阅读负担、控制成本并减少原文外传。

## 3. 已确认需求

以下主要来自 S3 用户回合 `f764c7ff-9528-4456-9c04-83aa5c64eb38` 与 `c4d51f7e-db99-47ba-8230-0383893e8eb2`。

| 方面 | 用户明确表达 |
| --- | --- |
| 消息范围 | 仅指定部分 QQ 群；未来支持多个 QQ 账号 |
| 规模 | 每天约 30,000 条消息；峰值流量尚未提供 |
| 内容 | 文本、链接；较多合并转发 / 聊天记录；大量图片或截图 |
| 完整性 | 全天候实时接收、尽量不漏；离线或断线后自动补齐；希望补录部署前历史 |
| 关注主题 | 科技、AI、网络、计算机技术 |
| 筛选方式 | 自然语言关注描述、关键词、自动发现新话题、阅读 / 收藏 / 忽略反馈、临时主题搜索 |
| 输出节奏 | 每小时整理高价值信息；每日关注主题摘要；网页信息流 |
| 来源定位 | 希望跳转 QQ 对应位置、查看前后上下文、应用内查看原文，并显示群名 / 发送人 / 时间 / 消息 ID |
| 通知 | Web 通知中心、手机浏览器 Web Push、QQ 私聊消息、邮件 |
| 存储与隐私 | 消息只保存几天后自动删除；原始聊天尽量不上传第三方 AI；可以调用外部 AI API |
| AI 模式 | 主要使用外部 AI API，成本可控；希望本地与外部两种方式可切换 |
| 运行设备 | 早期偏好本地电脑 / NAS，也接受云服务器；后来倾向云端全天运行，已有 2C2G40G 云服务器 |
| 排除范围 | 不需要自主聊天 |

“少上传原文”与“主要用外部 AI”需要具体的数据出站规则；两者均为确认的诉求，尚未确定怎样兼顾。Windows 本地开发与未来云端运行属于不同阶段，尚不能推断最终部署架构。

## 5. 历史技术路线（建议，未正式锁定）

S2 可见助手建议在后期转向“实时采集 / 导入 → 临时缓存 → 规则预过滤 → 主题聚合与 AI 重要性判断 → 摘要 → 来源回看与收藏 → 到期清理”。较早的永久归档、关系分析、长时记忆、全套机器人框架和大型数据库方案，不能沿用为当前必做范围。

历史候选与分工：

- NapCat：QQ 实时接入候选；SnowLuma 曾被讨论为另一接入候选。
- qq-chat-exporter：历史导出 / 补录候选，用户曾明确提供 `shuakami/qq-chat-exporter`。
- napcat-msg-store：实时事件持久化思路参考。
- QQMessageManager：增量处理、检查点、定时与重试思路参考。
- chat-analyzer：分析与摘要思路参考；确切仓库尚需核对。
- QBot：语义检索思路参考；确切仓库尚需核对。
- MaiBot / AstrBot：早期讨论过，但用户不需要自主聊天，后期建议第一版暂不引入。
- Python + SQLite / FTS5 + LLM + 简单 Web 页面：后期助手提出的轻量验证方案；数据库升级、向量检索等可后置。

这些仅记录历史讨论内容。本阶段没有安装、克隆或验证上述组件，也没有采纳不可读取的 S3 助手方案。

## 6. 尚未解决的问题

1. **接入与运行位置**：使用哪个 QQ 账号和群白名单？QQ 接入进程运行在 Windows 还是云端？2C2G40G 能否同时承载 QQ 接入、图片处理与分析任务，需要实测。
2. **完整性边界**：历史接口可回溯多远？离线消息、撤回 / 编辑、合并转发子消息与附件怎样记录？没有可核对的上游基准时，不能宣称 100% 完整。
3. **原文定位**：能否精确跳转客户端？若不行，应用内原文与上下文应作为首选可验收能力；过期删除后应如何提示？
4. **保留规则**：原文、图片、转发子消息、摘要、收藏和来源元数据分别保留多久？尚未确认任何具体天数。
5. **AI 与隐私**：允许外发哪些字段、是否脱敏、是否发送图片、如何控制 token / 费用？本地模式运行设备和模型尚未确定。
6. **分析质量**：高价值的评价标准、关注主题样例、误报 / 漏报容忍度、人工标注样本与验收指标待定义。
7. **MVP 边界**：四类通知、自动发现、反馈优化、临时搜索均是目标需求，但上线顺序尚未确定。
8. **技术选型**：接入组件版本、接口与许可证、开发语言 / Web 框架 / 数据库需核对并形成正式决策。
9. **资源预算**：月度 AI 支出、网络、磁盘与媒体缓存预算，群数量、峰值与部署前历史量待补充。
10. **历史缺口**：较新架构回复与其他未同步材料不可取得；取得原文后应补充证据并核对冲突，不追认现有建议为已定结论。
