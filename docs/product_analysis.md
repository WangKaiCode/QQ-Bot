## 业务目标与分析责任

用户面对大量 QQ 群消息，希望用较少阅读时间发现科技 / AI / 网络 / 计算机技术相关信息，并能回看证据。消息约 30,000 条 / 天、每小时整理与短期保存来自用户输入。需求清单中的“已确认”表示用户表达过该诉求，不表示它已成为经过完整分析、签署的实现规格。

乙方负责将输入转为使用场景、优先级建议、行为规格、可行性边界和验收案例；发现冲突与遗漏时先提出处理方案。甲方主要评估“是否帮助我、是否好用、是否符合实际使用”，不用自行制定架构或逐项批准技术细节。

## 核心使用场景

| 场景 | 用户想完成的事 | 乙方建议的产品行为 | 待体验验证 |
| --- | --- | --- | --- |
| 每小时快速浏览 | 不翻所有群，先看值得关注的信息 | 首页展示主题卡片：标题、短摘要、相关群、时间、证据条数与未读状态 | 一屏信息量、排序、摘要长度是否合适 |
| 回看来源 | 判断摘要是否可信，继续读上下文 | 卡片打开来源侧栏；显示消息段、群 / 人 / 时间与前后文，转发保留层级 | 回看是否方便；应用内定位能否满足主要需要 |
| 配置关注 | 用自己的话描述想看什么 | 提供自然语言关注框与可编辑关键词；先给样例预览再保存 | 是否容易表达，是否筛出想看的内容 |
| 每日回顾 | 快速了解一天重要进展 | 日报按主题合并小时结果，避免重复，保留证据和采集覆盖提示 | 日报是否冗长，是否遗漏重要主题 |
| 收藏 / 忽略 | 留下有价值的内容，减少重复推荐 | 在卡片上操作；说明收藏保存的内容与期限；首版记录行为，后续再评价推荐优化 | 收藏范围与忽略效果是否符合预期 |
| 采集异常 / 原文过期 | 知道结果是否可靠，避免误判无消息 | 在相关窗口显示断线 / 补录 / 未解析状态；来源过期明确提示 | 提示是否可理解且不干扰阅读 |

“阅读时间减少”和“信息有价值”是产品成功方向，尚无用户确认的数值目标。首轮体验用人工选择的例子观察，乙方据反馈提出可量化指标。

## 第一轮可评审材料

本轮实际交付：[来源阅读体验](web_usage.md)。先验证“选择群 → 找到原文 → 展开转发 → 连续查看前后文 → 解释导入错误”路径；不摆放没有功能的收藏 / 摘要按钮。消息最多的群默认选中，空文本消息保留在列表，图片与未知格式分别提示。同账号同群上下文边界明确，来源不足不编造。桌面双栏、窄屏上下布局；实现证据见 task013_validation.md，甲方反馈仍待收集。

先制作不含程序逻辑的页面线框与示例内容，覆盖首页信息流、主题详情 / 来源、关注配置、日报、收藏与采集状态。所有内容标为合成示例；它展示交互意图，不代表系统已接入 QQ、模型或完成实时筛选。

评审按用户任务组织：从首页找到感兴趣主题 → 查看证据 → 收藏或忽略 → 修改关注描述 → 查看一天回顾。甲方反馈用“哪里有用 / 哪里费解 / 哪里缺失 / 哪个结果不符合预期”表达即可；乙方转成需求和任务，不要求甲方写技术规格。

## 初步分析结论（乙方建议）

1. 来源回看应与摘要一起设计，不能等摘要完成后再补。
2. 对未解析转发、图片和未补齐区间显示输入覆盖状态；“没找到相关信息”与“缺少分析输入”必须区分。
3. 每小时卡片和日报避免简单重复；主题合并、迟到消息和更新说明需在设计中体现。
4. 收藏、原文回看和短期删除有冲突，需通过用户可见的保存范围与过期说明解决，不能默认为永久保留。
5. 原文少外传与外部 AI 优先有冲突，乙方应准备具体载荷样例及质量 / 成本影响，再让甲方判断接受程度。
6. 首版突出阅读和溯源；高级推荐、多渠道通知和多账号保留在路线图，不在当前无代码阶段实现。
