# 下一阶段开发计划（建议，待确认）

日期：2026-10-10。本文件是新提出的开发顺序，不代表历史已批准架构。下一阶段优先交付“可验证的采集与来源追溯”闭环，再接 AI 筛选与 Web 展示。

## 1. 先形成可审阅设计

完成需求矩阵、MVP 范围和技术决策草案，列出替代方案及约束：接入方式与运行位置、开发栈、数据格式、保留策略、AI 外发规则、成本上限。核对候选项目官方仓库、当前接口、许可证与 Windows / Linux 支持；记录核对日期和版本。

建议 MVP：单账号、指定群、文本 / 链接和结构化转发记录、短期本地存储、断线与导入状态、来源原文 / 上下文、关键词或主题筛选、每小时摘要与日报、Web 信息流 / 通知中心。图片第一步保留消息段和处理状态，是否引入 OCR 由真实样本决定。多账号、精确客户端跳转、反馈推荐、Web Push、QQ 私聊和邮件分后续增量交付。

**交付物**：需求矩阵、组件核对表、MVP 验收清单、技术决策草案。完成具体草案后，就重大选型、真实 QQ 接入和数据出站范围征求用户确认。

## 2. 实现离线样本到可查询来源

先用合成 / 脱敏事件，无需 QQ 凭据或外部 AI。实现事件标准化、持久化与幂等导入，保留账号 / 群 / 发送人 / 时间 / 上游消息 ID、采集来源和可用消息段。明确上游 ID 的作用域，不默认跨账号唯一。

建议最小实体：账号、群 / 会话、消息、消息段 / 转发子消息、导入批次、采集检查点、分析任务、摘要与证据关联。这里只是建模起点，不是已批准数据库 schema。

**验收**：相同样本重复导入不新增重复消息；不同账号的冲突 ID 可区分；乱序输入仍能查看正确时间上下文；转发子消息保留层级与来源；解析失败有状态和原因，不被静默丢弃。

## 3. 验证真实采集与补齐边界

在确认后接入一个账号和少量测试群。实现白名单、重连、重试、恢复扫描与失败记录；数据持久化成功后才推进相应检查点。采集与分析检查点分离。

完整性记录按账号 / 群 / 时间窗口报告：收到事件数、写入数、重复数、解析失败数、断线区间、补录尝试与结果、未解决区间。消息 ID 是否连续需验证；不能简单将 ID 跳号当作漏消息证据，也不能用自身计数证明上游全量。

**验收**：可控断线与进程重启后，恢复范围和未恢复范围均可查看；可获取的历史与实时消息合并后不重复；小型人工已知消息样本逐条核对；应用内能定位来源与上下文。QQ 客户端精确跳转另做能力验证，不能作为已实现前提。

## 4. 接入分析与最小 Web 界面

实现规则预过滤、关键词 / 自然语言主题配置、批量分析、每小时任务与日报；摘要必须关联证据消息。AI 提供可替换接口，先用模拟实现，再按批准规则调用外部 API。若本地模式暂不能运行，应明确其状态，不宣称模式切换已完成。

界面先展示信息流、通知中心、摘要、来源与上下文、采集状态、收藏 / 忽略。分析失败可重试，重复运行不重复生成通知。记录实际调用量和费用估算。

**验收**：合成一天约 30,000 条消息的回放可完成；处理时长、峰值内存、存储与队列积压有实测数据；不能用日均流量替代峰值测试。人工标注的小样本用于评估筛选误报 / 漏报；外发载荷符合批准规则。

## 5. 验证清理与部署

根据确认的分类保留规则实现到期清理，首次使用可预览待清理范围。检查收藏例外、附件和子消息联动；摘要证据过期时显示明确状态。随后在目标设备进行资源与稳定性测试，再确定云端部署方式。

**验收**：仅删除符合期限与规则的记录，收藏处理与批准策略一致；摘要不伪装成仍有原文；密钥不进入仓库或日志；2C2G40G 上的容量与负载结论有实测依据。部署、公开访问或账号通知发送前确认具体配置。

## 6. 实施前待补充

- 接入账号 / 测试群与运行位置。
- 原文、媒体、摘要、收藏的保留策略。
- AI 外发范围与月预算；本地模式目标设备。
- 优先通知渠道和高价值信息样例。
- 能取得的历史架构回复或导出样本。

这些信息未齐时，仍可完成候选核对、设计草案、合成样本和离线导入验证；真实接入、外部调用与删除策略的实现应以具体确认结果为准。
