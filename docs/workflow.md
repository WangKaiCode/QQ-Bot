## 流程与阶段交付

| 阶段 | 乙方交付 | 退出条件 |
| --- | --- | --- |
| 需求分析 | 需求编号、优先级建议、验收草案与未决清单 | MVP 范围与影响实施的业务边界已明确 |

## 状态和确认

需求确认与交付状态分开：

- 需求状态：已确认 / 待澄清 / 提议 / 已取消。
- 实现状态：未开始 / 进行中 / 已实现 / 已验收。
- 任务状态：待开始 / 进行中 / 待决策 / 待验收 / 完成。
- 决策状态：提议 / 已确认 / 已替代 / 已撤回。

甲方确认记录应有来源和日期。文档创建、乙方建议、甲方未回复、测试通过都不能代替甲方确认。已经获得的明确授权持续有效。

## 变更处理

收到变更后，先标注影响的需求、数据、接口、测试和进度。常规增量维护在任务范围内执行；重大改动先提出可审阅方案，按甲方要求确认后执行。既有文件不覆盖重建；修改前读取，保留仍有效的内容，对实质变化留下记录。

采用稳定编号追踪：`REQ-*` 需求、`TASK-*` 工作、`DEC-*` 决策。编号不重复使用；取消 / 替代项保留说明。验收案例随测试实现可再引入独立编号。

每次任务结束，更新任务表和 status.md；需求或决定变化时更新相应源文档，避免只在聊天中保留结论。记录变更日期、关联编号、验证方式与未决事项。重要交付写入 changelog.md。

工程设计完成后按需新增 `architecture.md`、`data_model.md`、`api.md`；有可运行代码后新增运行与配置说明；部署前再编写部署和恢复文档。这些文件应与实际实现同步，不能用空模板假装设计已完成。
